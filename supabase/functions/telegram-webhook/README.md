# telegram-webhook + telegram-link — деплой

Два Supabase Edge Function для фичи «Автодобавление ставок из Telegram-канала»
(CHANGELOG.md, 31.08.2026). Идея: добавляешь бота EDGE админом в свой
Telegram-канал — каждый новый пост уходит боту, модель (тот же принцип, что
и у распознавания скриншотов) пытается понять, похож ли текст на ставку, и
если да — кладёт в очередь на `telegram-import.html`. **Ничего не попадает в
дневник само** — каждую распознанную ставку нужно проверить и подтвердить
формой на `app.html`, как и при заполнении по скриншоту.

Функций две, и они РАЗНЫЕ по настройке JWT — это самое важное, что нужно не
перепутать при деплое:

| Функция | Кто дёргает | Verify JWT |
|---|---|---|
| `telegram-link` | Твой браузер (`telegram-import.html`), от твоего Supabase-логина | **ВКЛЮЧЁН** (по умолчанию, как у `parse-bet-screenshot`) |
| `telegram-webhook` | Сам Telegram (у него нет и не может быть твоего Supabase-токена) | **ВЫКЛЮЧЕН** — единственная такая функция в проекте |

Если оставить Verify JWT включённым на `telegram-webhook`, Supabase будет
отклонять вообще все запросы от Telegram ещё до того, как код функции
запустится — бот "не будет работать", и в логах будет просто 401, без
объяснений почему.

## Шаг 0. Схема БД

Сначала прогони `schema_milestone27.sql` в Supabase SQL Editor (три новые
таблицы: `telegram_links`, `telegram_pending_bets`, `telegram_parse_usage`).
Без этого шага обе функции будут падать при первом же обращении к базе.

## Шаг 1. Создать Telegram-бота

В любом Telegram-клиенте напиши **@BotFather** → `/newbot` → следуй
подсказкам (нужно имя и уникальный `@username`, обычно с окончанием `bot`).
В ответ придёт токен вида `123456789:AAExxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`
— это секрет, храни его так же аккуратно, как пароль (тот, кто его узнает,
сможет полностью управлять ботом).

## Шаг 2. Секреты

```
supabase secrets set TELEGRAM_BOT_TOKEN=<токен из шага 1>
supabase secrets set TELEGRAM_WEBHOOK_SECRET=<придумай сам, случайная строка от 20+ символов>
```

`TELEGRAM_WEBHOOK_SECRET` — не токен бота, а отдельная строка, которую
придумываешь сам (например, сгенерировать через `openssl rand -hex 24`).
Telegram будет присылать её обратно в каждом запросе к вебхуку — это то,
чем `telegram-webhook` отличает настоящие вызовы от Telegram от случайного
или злонамеренного запроса на тот же URL.

`ANTHROPIC_API_KEY` (и опционально `ANTHROPIC_MODEL`) должны быть уже
заданы из деплоя `parse-bet-screenshot` — обе функции используют один и тот
же секрет, повторно заводить не нужно. `SUPABASE_URL`/
`SUPABASE_SERVICE_ROLE_KEY` доступны автоматически, их тоже трогать не надо.

## Шаг 3. Деплой `telegram-link` (Verify JWT остаётся ВКЛЮЧЁН)

Через Dashboard: **Functions → Deploy a new function → Via Editor**, вставить
код `supabase/functions/telegram-link/index.ts` целиком, **Deploy function**.
Проверить на вкладке Settings этой функции, что «Verify JWT with legacy
secret» включён (стандартное состояние — трогать не нужно).

Через CLI: `supabase functions deploy telegram-link`.

## Шаг 4. Деплой `telegram-webhook` (Verify JWT нужно ВЫКЛЮЧИТЬ)

Через CLI это один флаг:
```
supabase functions deploy telegram-webhook --no-verify-jwt
```

Через Dashboard флага при первом деплое через редактор нет — задеплой как
обычно (Deploy a new function → Via Editor → вставить код → Deploy), а
**после** этого зайди в саму функцию → вкладка **Settings** → выключи
переключатель **«Verify JWT with legacy secret»** → сохрани. Без этого шага
функция задеплоится, но будет молча отклонять всё, что присылает Telegram.

## Шаг 5. Зарегистрировать webhook у Telegram (один раз)

Это обычный вызов API Telegram с токеном бота, не имеет отношения к
Supabase CLI — можно выполнить из любого терминала с `curl`:

```
curl "https://api.telegram.org/bot<ТОКЕН_БОТА>/setWebhook" \
  -d "url=https://<project-ref>.supabase.co/functions/v1/telegram-webhook" \
  -d "secret_token=<та же строка, что в TELEGRAM_WEBHOOK_SECRET>" \
  -d "allowed_updates=[\"channel_post\"]"
```

`project-ref` — там же, где для CLI (Dashboard → Settings → General →
Reference ID). В ответ Telegram должен вернуть `{"ok":true,"result":true,...}`
— это значит, что регистрация прошла. Проверить состояние в любой момент
можно запросом `.../getWebhookInfo` (без параметров, тем же токеном).

Если позже понадобится сменить `TELEGRAM_WEBHOOK_SECRET` — `setWebhook`
нужно вызвать заново с новым значением, старое перестанет приниматься сразу
после смены секрета функции.

## Шаг 6. Добавить бота в канал

В настройках своего Telegram-канала → **Администраторы** → добавить бота по
его `@username` из шага 1. Прав достаточно минимальных — «видеть посты»
(«Post Messages» боту публиковать не нужно, только читать канал). Без этого
шага бот физически не получает посты канала, даже если webhook настроен
правильно — Telegram не присылает апдейты из каналов, где бота нет.

## Шаг 7. Привязать канал в EDGE

На `telegram-import.html` → **«Сгенерировать новый код»** (если ещё не
генерировался) → скопировать код вида `EDGE-XXXXXX` → опубликовать его
**одним отдельным постом** прямо в канале, куда добавлен бот. В течение
нескольких секунд бот подтвердит привязку ответным сообщением в канале и
статус на странице обновится (может понадобиться обновить саму страницу).
После подтверждения пост с кодом можно удалить — он больше не нужен.

## Проверка после деплоя

Опубликуй в привязанном канале тестовый пост в духе «Ставлю на Vitality
-1.5 карты, кэф 1.85, 100$ на Pinnacle» — в течение нескольких секунд он
должен появиться в очереди на `telegram-import.html`. Если не появился —
смотри Supabase Dashboard → Functions → telegram-webhook → Logs, там будут
`console.error` с причиной (неверный секрет, не заданы переменные, ошибка
Anthropic и т.п. — функция всегда отвечает Telegram `200 ok`, поэтому сам
Telegram никогда не покажет ошибку, диагностика только через Logs).

## Стоимость

Как и `parse-bet-screenshot` — реальные деньги за каждый вызов модели, но
текстовый вызов на порядок дешевле вызова с картинкой. Действует отдельный
месячный лимит `MONTHLY_TELEGRAM_LIMIT = 1000` постов на пользователя
(константа в `telegram-webhook/index.ts`) — выше, чем у скриншотов (100),
именно из-за разницы в цене, но всё ещё конечный, чтобы активный канал с
частыми постами не генерировал неограниченный счёт. Таблица
`telegram_parse_usage` — тот же паттерн read-then-write (не атомарная
транзакция) и тот же фейл-открыто, что у `screenshot_parse_usage`.

## Что намеренно не сделано

Обрабатываются только `channel_post` (посты в канале) — личные сообщения
боту (DM/приватный чат) в этой версии не поддерживаются, хотя архитектурно
это было бы несложно добавить отдельным веткой в том же webhook. Осознанно
отложено — исходный запрос был именно про Telegram-канал, а не личный чат.

## Тестирование без реального бота

В песочнице нет доступа ни к Telegram Bot API, ни к ключу Anthropic, так что
проверить именно факт распознавания реального поста нельзя. Что покрыто
тестом — вся клиентская часть (`app_test8/test_telegram_import.py`): статус
привязки, генерация кода, смена целевого канала, отвязка, очередь на
подтверждение (карточки, «Отклонить», «Заполнить и добавить»), переиспользование
инфраструктуры очереди скриншотов на `app.html?tg=<id>`, и то, что
подтверждённая ставка удаляется из очереди после сохранения. Мок в
`app_test8/supabase-client.js` эмулирует то, что в реальном приложении
сделали бы `telegram-link` (действия `generate_code`/`set_channel`/`unlink`
через `functionsApi.invoke`) и `telegram-webhook` (вставка в
`telegram_pending_bets` и подтверждение `telegram_links` — в тесте
симулируется напрямую через `sessionStorage`, как и в других тестах на
серверные эффекты, которые мок не производит сам).
