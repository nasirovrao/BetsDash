# EDGE — история проекта

Этот файл — не журнал последних решений (для этого есть `CHANGELOG.md`, он
специально короткий и смотрит только вперёд/чуть назад), а полный путь
проекта от первой версии схемы базы до сегодняшнего дня, одним связным
рассказом. Веду его с 30.08.2026 и обновляю при каждой новой вехе — так,
чтобы через полгода можно было открыть один файл и понять, откуда что взялось
и почему устроено именно так, а не иначе.

**Честно про полноту.** Хронология по SQL-миграциям (раздел «Вехи») —
надёжная: она построена по самим файлам `schema_milestoneN.sql` и их
собственным датированным комментариям, а не по памяти. А часть решений,
обсуждавшихся в переписке до того, как я начал вести `CHANGELOG.md` (Milestone
22), могла нигде не осесть в файлах — у меня физически нет доступа к
переписке старше этого момента, пока кто-то не пришлёт скриншот (так
нашлись «Автодобавление ставок из Telegram»/«Парсинг скриншота» в очереди
CHANGELOG.md, следующим — целиком раздел «Исток» ниже, включая тот факт,
что до Supabase сайт вообще был статическим, а затем — раздел «26.08.2026 в
деталях» ниже, про редизайн карточек ставок и хардненинг перед бетой; позже
так же нашлась и доработана детальная история Milestone 7–16 — публичный
профиль, отказ от привязки букмекерского API, снятие «запросить доступ»,
реальный production-баг в миграции Milestone 16, общий импорт Excel/CSV и
история выбора шрифта AST19, а заодно исправлены две собственные более
ранние неточности в этом файле про источник EDGE 2.0 и статус редизайна
`.brand-mark`; следующим — полная история появления EDGE 3.0 «ICE SLATE»
через скилл `ui-ux-pro-max`, включая происхождение трёх скиллов проекта и
одну пойманную попытку инъекции через постороннее содержимое; следующим —
детали Milestone 17 (живая проверка утечки до/после фикса), реальный баг
видимости CLV Tracker из-за `.maybeSingle()` на многострочной таблице,
двухэтапная история поля «Дисциплина», и полировка публичного профиля до
паритета с приватным дашбордом). Если по ходу всплывёт ещё что-то
забытое — присылай, дополню.

## Что такое EDGE

Многостраничный статический сайт (чистый HTML/CSS/JS, без сборщика и
бэкенд-фреймворка) для трекинга ставок на спорт/киберспорт — личный дневник
+ публичные каналы с совместным ведением. База и авторизация — Supabase
(Postgres + Auth + Row Level Security), рабочая копия на диске —
`cybervalue_app/`. Домен изначально назывался CyberValue, переименован в
EDGE по ходу разработки (видно по самим файлам миграций — Milestone 1–2 ещё
"CyberValue App", дальше уже "CyberValue / EDGE").

## Что не меняется от вехи к вехе (архитектурные константы)

Несколько решений, принятых рано, действуют на протяжении всего проекта и
важны для понимания почти любой миграции ниже:

- **Каналы.** С Milestone 8 каждая строка `bets`/`withdrawals`/`edges`/
  `settings` размечена `channel` — `'default'` (личный дневник) или именованный
  публичный канал (`'cybervalue'` изначально, с Milestone 23 — любое имя в
  формате слага). Приватные страницы всегда показывают только свой канал;
  переключение — через `?channel=&owner=`.
- **Доступ к каналу — «владелец приглашает».** С Milestone 12/14/15: владелец
  зовёт по email, приглашённый просто принимает, отдельного шага
  запрос→одобрение нет (было в 12/14, убрано в 15 по прямой просьбе
  пользователя).
- **RLS — единственная реальная граница доступа.** Anon-ключ Supabase лежит
  открыто в клиентском JS (это нормально для Supabase), значит вся защита
  держится на политиках в базе, а не на том, что фронтенд сам фильтрует
  данные. Дважды (Milestone 17, 18) именно это допущение спасало от реальных
  дыр — см. ниже.
- **Слоёный CSS.** `styles.css` (база) → `styles-edge2.css` → `styles-edge3.css`
  → `styles-edge4.css` → `styles-edge5.css`, каждый следующий слой только
  переопределяет предыдущий, ничего не выпиливая. Не привязан 1:1 к номерам
  Milestone (это отдельная, более редкая нумерация — см. раздел «Дизайн-
  система» ниже).

## Исток (до Milestone 1 — восстановлено по скриншотам переписки)

Проект начался не с Supabase и не с кода — с обычного текстового журнала
ставок, который пользователь вёл сам, отдельными строками. Задача была
превратить его в сайт: чтобы можно было самому добавлять записи и ставить
метки, и чтобы каждый залогиненный пользователь видел только свои данные.
Калькулятор Келли, который был в исходном журнале, попросили убрать сразу —
в текущем EDGE его нет и не было ни в одной последующей версии.

Ключевое архитектурное решение здесь: авторизация с индивидуальными данными
для каждого пользователя — это уже не статичный сайт (сам по себе
достаточный для GitHub Pages), а нужен настоящий бэкенд с базой. Выбор пал
на Supabase (готовые auth + Postgres, без своего сервера) — это решение с
тех пор ни разу не пересматривалось и остаётся фундаментом всего, что
описано в «Вехах» ниже. «Метки» на ставках изначально задумывались как
что-то новое, но выяснилось, что для этого уже есть механика — поле
«Эдж-паттерн»/реестр эджей — и её просто взяли как есть, не заводя
отдельную систему тегов.

**Milestone 1** (`schema.sql`) — исходная схема (таблица `bets` + RLS,
подробно в «Вехах» ниже) и первая рабочая страница — «Ставки»
(добавление/таблица/удаление), задеплоенная на GitHub Pages в репозиторий
`BetsDash` (сайт статический, ES-модули не грузятся через `file://`, нужен
именно деплой, не открытие файла напрямую). Проверено «в живую»: регистрация,
добавление ставки, значение переживает обновление страницы.

Здесь же — происхождение паттерна `styles.css?v=N`, который всё ещё в ходу
сегодня (`?v=29` на актуальных страницах): после Milestone 2 браузер
показывал недостающие стили — не баг вёрстки, а обычное кэширование
(файл лежал под тем же именем, что и в Milestone 1). Почему-то помогло не
сразу: почистить руками нельзя было положиться на пользователя каждый раз,
поэтому решили раз и навсегда версионировать ссылку на файл — с тех пор
любое обновление `styles.css` сопровождается бампом `?v=`.

**Milestone 2** — `settings` (стартовый банк, от которого считаются «Банк» и
«Прирост банка» на Дашборде) и вывод средств, плюс страницы «Дашборд» и
«Выводы и банк», и общая навигация сразу на всю задуманную структуру (9
пунктов — 6 из них временно заглушки «🚧 скоро», без битых ссылок).

**Первый ребрендинг (тоже 25.08.2026, между Milestone 2 и 3).** Самая первая
версия визуала называлась «CyberValue» — золотисто-коричневая «терминальная»
палитра, шрифт Newsreader. Её полностью переделали в том же заходе: фон
графитово-чёрный, акцент — электрик-индиго (`#7c6cff` — то самое значение,
которое до сих пор лежит в переменной `--gold` в `styles.css`: имя
переменной не переименовывали, чтобы не трогать разметку, поменяли только
смысл), Newsreader → Space Grotesk (заголовки/лого) + Inter (текст/формы),
радиус скругления 4px → 10px. Название сменилось с «CyberValue» на «EDGE.» —
короче и по смыслу (поиск эджа в ставках), с акцентной точкой. **Это и есть
происхождение сегодняшнего `styles.css`** — то, что в разделе «Дизайн-
система» ниже названо «исходной базой», само уже было редизайном; более
раннего файла с золотой CyberValue-палитрой не сохранилось, она известна
только по этому описанию.

Тогда же появился фирменный SVG-значок у логотипа (`.brand-mark`, виден в
шапке каждой страницы): пользователь просил что-то в духе значка Аегиса из
Dota — иконки и арт самой игры принадлежат Valve, использовать напрямую
нельзя, поэтому сделан самостоятельный геометрический знак «в той же
атмосфере», без прямого заимствования.

Сразу следом, ещё до Milestone 3: страница входа переделана в сплит-экран
(слева питч с фичами, справа форма, на мобиле хиро прячется), поле
«Букмекер» на «Ставки» стало запоминать когда-либо вписанные значения через
нативный HTML `<datalist>` (жив и сегодня, без отдельной таблицы в базе) —
и здесь же, ещё на этом самом раннем этапе, пользователь впервые попросил
автодобавление ставок по скриншоту. Уже тогда было понятно, что это
отдельная крупная задача (нужна модель с поддержкой изображений через
защищённую серверную функцию — в Supabase это Edge Function — либо готовый
OCR-сервис), поэтому отложена; тот же запрос всплыл повторно много позже
(см. очередь в CHANGELOG.md) — это не новая идея, а напоминание о старой.

## 26.08.2026 в деталях (восстановлено по скриншотам переписки)

Раздел «Вехи» ниже про этот день опирается на файлы миграций
(`schema_milestone3.sql`, `schema_milestone4.sql`) — они честно фиксируют
изменения в базе, но почти ничего не говорят про фронтенд, которого в тот
день было гораздо больше. По новой пачке скриншотов картина дня выглядит
так.

Тогда же, помимо переноса истории и RLS-фикса, страница «Ставки» пережила
первый настоящий редизайн: широкую таблицу заменили на карточки ставок,
сгруппированные по месяцам — тот же формат, что жив и сегодня. Сознательно
**не стали** переносить из старого журнала CLV%, хедж и кэф закрытия, а
также калькулятор Келли (тот самый, убранный ещё на самом старте — см.
«Исток» выше) — решили, что это отдельный, более сложный трекер (со
временем он и появился отдельно, как CLV Tracker в Milestone 5), а не
часть базовой карточки ставки. В карточке сразу сделали разрешение Pending
прямо на месте, без отдельной формы редактирования — клик по исходу
обновлял статус ставки тут же.

Логика определения рынка и команды по тексту (поля «Пик»/«Матч» на форме
ставки, ключевые слова для определения типа рынка, нормализация алиасов
команд — LevelUP/Heroic/paiN/Ninjas in Pyjamas/Yandex и варианты написания)
взята как есть из старого текстового журнала, без переделки — донастроили
только сами алиасы под названия, реально встречавшиеся в ставках.

В тот же день — пачка из 4 мелких UI-багов: в Экспрессах, в Дуэлях, в
Заметках и обрезание контента на мобильных (все найдены и починены в одном
заходе). Отдельно всплыл и был исправлен баг с именем дуэлянта,
показывавшимся вместо названия матча — перепутанные поля в карточке.

**Хардненинг перед бетой.** Отдельным блоком в тот же день — вещи, без
которых показывать сайт кому-то ещё было рискованно: подтверждение перед
удалением ставки (раньше кнопка удаляла сразу, без «уверены?»),
полноценное редактирование уже добавленной ставки (раньше можно было
только добавить/удалить, не поправить), восстановление пароля, график
банка/капитала на Дашборде и умные фильтры в ленте ставок. Единственная
часть этого блока, которая реально трогала базу, — усиление RLS
(`WITH CHECK` на UPDATE), и это тот же самый `schema_milestone4.sql`,
что уже описан как Milestone 4 в «Вехах» ниже; всё остальное — чистый
фронтенд, без миграции.

Позже тем же вечером — визуальная полировка графика банка/капитала, а в
самом конце дня — финальный баг-свип: дефолтная дата в форме ставки
бралась в UTC вместо локальной таймзоны пользователя, из-за чего «сегодня»
вечером могло записаться как «завтра» — исправлено. Здесь же пользователю
показали, как самому добавить новую дисциплину прямо в `app.html` — список
дисциплин тогда ещё не был вынесен в настройки, это случится только в
Milestone 20.

### Как строились CLV Tracker и реестр эджей (Milestone 5–6, восстановлено по скриншотам переписки)

Ещё один заход того же периода, найденный отдельно — подробности того, как
именно дошли до сегодняшнего вида CLV Tracker и «Найденные эджи», которые
в «Вехах» ниже описаны только итогом.

**CLV Tracker не сразу стал таким, какой он сегодня.** Первая версия по
ошибке скопировала модель обычного журнала — с исходами Win/Loss/Push. Это
неверно по смыслу: в CLV Tracker нет проигрыша как такового — пойманный
эдж либо ещё «В игре» (Pending), либо закрыт одним из двух способов:
перекрыт на другой стороне/у другого букмекера (**Хедж**) или продан
букмекером напрямую (**Продана**, кэшаут). После того как это указали
прямо, статусы переделали на эти три, а Win/Loss/Push убрали из CLV
Tracker полностью. Для «Продана» профит вписывается вручную (кэшаут-сумму
назначает букмекер, формулой её не вывести), а для «Хедж» — считается сам
по формуле гарантированного результата classic back/hedge: при ставке
`stake` по кэфу входа `entryOdds` и перекрытии по кэфу `hedgeOdds`, сумма
хеджирующей ставки `hedgeStake = stake × entryOdds / hedgeOdds`, а итоговый
профит `stake × entryOdds − stake − hedgeStake` (`computeHedgeProfit` в
`lib.js`) — одинаков независимо от того, какая сторона в итоге зайдёт.
Пока статус «В игре» — профит показывает прочерк; как только вписан кэф
хеджа, таблица сразу показывает предпросмотр ожидаемого профита с пометкой
«~ ожид.», который живьём пересчитывается по мере правки формы. Строка
записи целиком кликабельна (открывает её на редактирование), не только
маленькая иконка-карандаш. Включается CLV Tracker не через отдельную
админ-панель (её нет и не планировалась на этом этапе) — вручную, через
`settings.clv_tracker_enabled = true` в Table Editor Supabase на
конкретного пользователя, после разового запуска `schema_milestone5.sql`.

**Реальный баг видимости, найденный позже (28.08.2026, восстановлено по
скриншотам переписки).** Пользователь включил флаг вручную через Table
Editor, но пункт «CLV Tracker» в навигации не появился («всё включено, но
не отображается»). Причина не в UI, а в самом запросе к базе: функция
`isClvEnabled()` в `supabase-client.js` читала таблицу `settings` без
фильтра по пользователю и ждала ровно одну строку через `.maybeSingle()`
— но `settings` хранит одну строку НА КАЖДЫЙ КАНАЛ, а не на пользователя
(личный дневник + Cybervalue — уже минимум две строки). Как только строк
стало больше одной, Supabase вернул ошибку «ожидалась одна строка, а их
несколько», и функция молча решила, что флаг выключен, хотя в нужной
строке честно стояло `true`. Починено явным `.eq('user_id', ...)` и
логикой «включено хотя бы в одной строке» вместо ожидания единственной —
заодно ужесточён локальный тестовый мок (раньше он был мягче настоящего
Supabase и не воспроизводил эту рассинхронизацию).

**«Найденные эджи» умели появляться только задним числом.** До правки эдж
на этой странице возникал неявно: сначала нужно было завести ставку и
вписать метку в поле «Эдж-паттерн», и только тогда карточка появлялась
сама — отдельной кнопки «добавить эдж» не было вообще. Добавили форму
сверху страницы (название + необязательное описание) — карточка
появляется сразу же, даже с нулём ставок, и название сразу попадает в
автодополнение поля «Эдж-паттерн» на форме ставки. Хранится в отдельной
таблице `edges` (`schema_milestone6.sql`) — до её создания страница
продолжает работать по-старому (эджи только из тегов ставок), просто форма
добавления недоступна и явно об этом предупреждает.

**Заодно — визуальная и структурная полировка вокруг обеих фич,** не
зафиксированная отдельным Milestone, потому что чисто фронтенд и без
собственной миграции: страницы Команды/Рынки/По букмекерам получили
кликабельные карточки с полоской винрейта вместо плоских таблиц (тот же
паттерн детальной статистики, что уже был у эджей); в детальные таблицы
ставок (Рынки/Команды/Эджи) добавлена колонка «Букмекер» (на самой
странице «По букмекерам» её нет — там и так все строки одного букмекера);
жирный нативный скроллбар под широкими таблицами заменён на тонкий (6px)
в цвет темы, который появляется только когда таблица реально не влезает;
таблицы избавлены от жёсткого `min-width`, текстовые колонки теперь
переносятся по словам — горизонтальный скролл почти не нужен на обычных
экранах. Список типов ставки сокращён до Pre/Live/Хедж (убрана
«Попанская», «Pre-value»/«Live value» переименованы в короткие «Pre»/
«Live») — у старых ставок в базе прежние значения остаются как есть,
просто перестают совпадать с новыми пунктами списка до ручного
пересохранения. Из «Сегментации» убран блок «Уверенность» (звёздный
рейтинг), остался только разбор по типу ставки.

На дашборде появился блок «Текущая серия» — заголовок вида «6 поражений
подряд» (или побед) плюс ряд точек по последним до 10 сыгранным ставкам,
самая свежая выделена кольцом; Push обрывает серию (`computeStreak` в
`dashboard.html`). Разбивку по турниру и по месяцу сначала сделали двумя
отдельными вкладками нав-бара (по образцу остальных разбивок), но по
следующей просьбе свернули прямо в Дашборд как два фильтра над карточками
статистики — выбор турнира/месяца пересчитывает и карточки, и «Текущую
серию» на лету, без перехода на другую страницу; карточки «Банк»/«Прирост
банка» на активном фильтре скрываются (это показатели за всю историю
целиком, «банк за один турнир» не имеет смысла), а сетка карточек при этом
переключается с 4 колонок на 3, чтобы 6 оставшихся карточек не оставляли
пустую серую ячейку в углу — этот конкретный визуальный баг нашли и
починили по прямой просьбе «найди на скрине уродство».

## Вехи

### 25.08.2026 — старт

**Milestone 1** (`schema.sql`) — исходная схема: единственная таблица `bets`
(дата, дисциплина, букмекер, турнир, матч, пик, кэф, флет-множитель, сумма,
исход Win/Loss/Push/Pending, тип ставки, уверенность, эдж-тег, live-флаг) +
RLS на основе `auth.uid() = user_id`. (Контекст создания — выше, раздел
«Исток».)

**Milestone 2** — `settings` (стартовый банк, от которого считаются «Банк» и
«Прирост банка» на Дашборде) и вывод средств.

### 26.08.2026 — данные и первые фичи

**Milestone 3** — перенос истории из старого журнала: статус `Sold`
(досрочная продажа), поля `manual_profit`/`notes`/`est_prob`/`date_added`.

**Milestone 4** — усиление RLS: политики `UPDATE` проверяли только какую
строку МОЖНО редактировать (`USING`), но не какие значения в неё МОЖНО
записать (`WITH CHECK`) — теоретически можно было переписать `user_id` в
своей же строке на чужой. Добавлен `WITH CHECK`. (Эта же дыра тихо вернётся
в Milestone 18 — см. ниже.)

**Milestone 5** — CLV Tracker: отдельный, независимый от основного журнала
трекер пойманных эджей (`clv_entries`), статусы Pending/Hedged/Sold вместо
обычного Win/Loss. Включается вручную через `settings.clv_tracker_enabled`
(нет отдельной админ-панели — осознанно простое решение на старте беты).

**Milestone 6** — реестр эджей: можно завести именованный паттерн заранее, а
не только неявно через тег в форме ставки.

### 27.08.2026 — публичность и совместная работа (самый насыщенный день)

**Milestone 7** — публичный профиль: таблица `profiles` (username, имя,
описание, `is_public`), плюс вторая select-политика на
`bets`/`withdrawals`/`settings`/`edges`, разрешающая читать данные владельца
анонимно, если у него `is_public = true`.

**Milestone 8** — разделение на каналы: личный дневник и канал Cybervalue
становятся двумя независимыми наборами данных внутри одного аккаунта
(`channel = 'default' | 'cybervalue'`).

**Milestone 9** — логотип канала на публичном профиле: колонка
`profiles.logo_url` + бакет Storage `profile-logos` с RLS по папке
пользователя.

**Milestone 10** — лёгкий сигнал доверия против «тихой правки истории
задним числом»: `updated_at` (трогается на каждое изменение) и `settled_at`
(фиксируется один раз, при первом переходе из Pending).

**Milestone 11** — тот же сигнал, но конкретнее: триггер сам считает
короткий diff по значимым полям (пик/результат/кэф/сумма) в `edit_note`,
вместо двух голых дат в тултипе. Осознанно хранится только последний diff,
не полная история правок — это лёгкий сигнал доверия, не аудит-лог.

### Как строился публичный Cybervalue-профиль и первый разбор MVP (Milestone 7–10, восстановлено по скриншотам переписки)

Ещё одна деталь того же дня, найденная отдельно, — с чего конкретно начался
публичный канал Cybervalue, и первый настоящий разбор, что такое MVP для
платформы (задолго до решения от 30.08.2026 выше, но по сути та же мысль).

**W/L/P и экспрессы получили визуальную доработку прямо перед стартом
публичности.** Разбивка «15 / 11 / 1» текстом заменена на цветные пилюли —
победы зелёным, поражения красным, пуши приглушённым серым, с подписями
W/L/P — правка в общем компоненте, поэтому применилась сразу и на
Дашборде, и во всех детальных разбивках. Отдельно обнаружилось, что
экспрессы можно было залогировать только текстом в поле «Пик» с ручным
итоговым кэфом — добавлен настоящий конструктор: чекбокс «Это экспресс»
прячет поля «Матч»/«Пик» и открывает построчный ввод ног (описание + кэф
каждой), итоговый кэф считается как произведение кэфов ног и не
редактируется руками. Новой миграции не потребовалось — легло в уже
существующие поля ставки.

**Публичный Cybervalue-профиль начался с прямого запроса**: «нужна
публичная версия канала, я сам буду заполнять туда данные, но чтобы
обычным пользователям была видна вся статистика». Решили сразу показывать
всё как есть (без урезания сумм до относительных величин) и открывать не
только общий дашборд, а все разбивки целиком. Отсюда — `profile-settings.html`
(юзернейм + галочка публичности) и `public.html?u=` (открывается без входа
в аккаунт). Важная деталь очерёдности миграций: `schema_milestone7.sql`
(вторая select-политика «читать чужие строки, если `is_public=true`»)
физически зависит от уже накаченного `schema_milestone6.sql` (таблицы
`edges`), потому что публичная политика распространяется в том числе и на
неё — прогонять их нужно строго по номерам, не переставляя местами.

Сразу выяснилось, что данные владельца и канала Cybervalue не должны быть
одной и той же таблицей — «все данные моей таблицы не имеют ничего общего
с Cybervalue, буду заносить сам, пусть стартует пустым». Отсюда и родилось
разделение на `channel` (Milestone 8) — до этого момента идеи отдельного
канала как концепции ещё не было, только личный дневник. На публичном
дашборде тогда же появилась карточка «В игре» — считает ставки со статусом
Pending отдельной цифрой.

**Логотип канала** (Milestone 9) добавлен по прямому референсу — пользователь
прислал, как должно выглядеть (кружок-аватар слева от названия, бейдж
статуса уходит под название). Хранится в Storage-бакете `profile-logos` с
политиками «читать может кто угодно, писать/удалять — только владелец
своей папки». Здесь же поймали и починили баг с кэш-бастингом: `?t=...`
в конце ссылки на картинку (чтобы браузер не показывал старую версию после
перезагрузки лого) в отдельных случаях ломал саму ссылку — исправлено до
того, как это всплыло на боевом Supabase. Отдельно — баг с юзернеймом:
поле принимало `Cybervalue` с заглавной буквы, база отклоняла (ограничение
требует строчные латинские буквы), а понижение регистра в коде срабатывало
только в момент сохранения. Исправлено на уровне поля — регистр приводится
на лету при вводе, плюс отдельная проверка до обращения к Supabase, которая
явно называет причину (включая случай, когда буквы визуально похожи на
латинские, но набраны в русской раскладке) вместо сырой ошибки Postgres.

**Первый разбор MVP-приоритетов** случился здесь же, по прямому вопросу
«что добавить первоочередно, что попозже». Формулировка, к которой пришли:
смысл MVP не в том, чтобы утрамбовать больше фич, а в том, чтобы как можно
быстрее проверить тезис «верифицированный трек-рекорд + красивая подача
заставит людей заходить, доверять и возвращаться» — всё, что не работает на
эту проверку напрямую, откладывается. Первый эшелон (сделано в тот же
день, см. Milestone 10 выше): доверие к цифрам — метка правки задним числом
плюс запрет тихо переписывать прошлое; превью ссылки при шаринге в
Telegram/VK (`og:image`/`og:description`, статичный баннер бренда EDGE, не
персональный под канал — персонализация потребовала бы серверной функции,
которой на статическом хостинге нет); объяснительный блок прямо на
публичной странице, что за цифрам можно верить и почему; проверка на
мобильном. Второй эшелон (по вкусу, не блокирует запуск с одним каппером):
каталог/лидерборд из нескольких капперов (бессмысленен, пока в системе
один публичный профиль), подписка/уведомления о новых ставках, монетизация
через внешние Boosty/DonationAlerts (без собственного биллинга на этом
этапе), самостоятельная регистрация других капперов (пока — по сути один
Supabase-аккаунт, для второго каппера либо заводить вручную, либо позже
делать нормальный self-signup). Третий эшелон (после того как гипотеза
подтвердится): свой домен и бренд, настоящий биллинг вместо донатов,
модерация чужих профилей, аналитика посещаемости, масштабирование за
пределы русскоязычной аудитории.

Про домен отдельно уточнили: переезд на купленный домен (в разговоре —
`betedge.com` как пример) технически тривиален именно потому, что весь
проект — чистый HTML/CSS/JS + Supabase без фреймворка и привязки к
конкретному хостингу — направить домен через CNAME на GitHub Pages или
вообще перенести файлы на Vercel/Netlify/Cloudflare Pages одним
драг-н-дропом, плюс не забыть добавить новый домен в Supabase → Auth → URL
Configuration (иначе письма подтверждения/сброса пароля будут вести на
старый адрес). Код и база данных разницы не почувствуют.

**Важное решение об архитектуре доверия к данным, принятое здесь же:
привязка личного кабинета букмекера по API — отклонена как направление.**
Пользователь спросил про два усиления: ставки со скриншотов и привязка
букмекерского аккаунта по API. С распознаванием скриншотов согласились —
технически ложится без лишних сущностей (одна Supabase Edge Function,
держащая ключ модели на сервере, а не в статическом фронтенде, картинка
внутрь → структурированный ответ наружу), при обязательном условии, что
подтверждение человеком перед сохранением — обязательный шаг, а не опция
(иначе теряется сам смысл верифицируемости, за который борется весь
проект). Это и первая в проекте статья реальных расходов — вызов модели с
картинкой стоит не ноль, раньше всё держалось на бесплатных лимитах.
Привязка же личного кабинета букмекера по API — **отклонена полностью, не
отложена**: ни у одного массового букмекера (1xBet/Fonbet/Winline/Pinnacle
и т.п.) нет официального публичного API, отдающего историю ставок
конкретного игрока по его кабинету — сервиса в духе «Plaid для беттинга» в
нише не существует. Единственный технический способ получить это без
официального API — залогиниться от имени пользователя и скрейпить историю
из его личного кабинета, а это означает хранение чужих учётных данных
финансового по сути сервиса (серьёзная ответственность и репутационный
риск), плюс хрупкость на любой редизайн личного кабинета букмекера.
Вместо этого предложена рабочая альтернатива — **партнёрские (affiliate)
API букмекеров**: не чтение чужого личного кабинета, а официальная
статистика по игрокам, которых сам продукт привёл по своей партнёрской
ссылке (регистрации, депозиты, иногда активность) — закрывает разом и
вопрос доверия к данным (данные от источника, не введённые вручную), и
вопрос монетизации. Не пятиминутная задача (нужна официальная регистрация
партнёром у конкретных букмекеров, орг-работа, не только код), поэтому
запаркована как отдельное стратегическое направление, а не встроена в
ближайший MVP.

**Реализовано по итогам этого разбора в тот же день** (это и есть техническая
сторона Milestone 10 выше): `settled_at` фиксируется один раз при первом
выходе из Pending, `updated_at` — на каждое изменение; если правка приходит
уже после того, как `updated_at` обгоняет `settled_at` больше чем на
несколько секунд — в таблице появляется бейдж «✎ изменено» с тултипом,
через триггер в базе (`schema_milestone10.sql`), так что это ловит даже
прямое редактирование через Table Editor в Supabase, не только форму на
сайте. На публичном профиле под шапкой — короткая честная приписка про
метки времени и правки задним числом. По пути поймали реальный мобильный
баг: длинный бейдж «Публичный профиль · верифицированные данные · только
чтение» на узких экранах разрывал страницу по горизонтали — почищено
через обрезание многоточием вместо переполнения.

**Три идеи, оставленные на будущее по итогам этого же разговора** (не
реализованы в найденных скриншотах, но зафиксированы как направления):
парсинг ставок напрямую из Telegram-каналов ДРУГИХ капперов с
автодублированием на сайт при выполнении заданных условий — это не то же
самое, что «импортировать свой собственный канал» из очереди CHANGELOG.md,
здесь речь про чужие каналы как источник контента; редизайн визуального
языка сайта по референсам premium fintech/trading-продуктов (в разговоре
изучались Stripe, Mercury, Linear, Ramp, Wise, Vercel, Attio, Raycast —
принципы: цвет означает состояние, а не украшение; цифры табличным
моноширинным шрифтом; сдержанность и повторяемость важнее декоративности)
— и правка `.brand-mark` — пользователю показалось, что ромбовидный значок
похож на логотип Ethereum, попросили переделать «под уже новый стиль».

**Уточнение 30.08.2026 (по более поздним скриншотам той же переписки):** обе
эти идеи были доведены до конца, и обе относятся не к EDGE 3.0, а к **EDGE
2.0**. Сама редизайн-сессия по фин-тех референсам (Stripe/Mercury/Linear и
т.д.) — это и есть исходная история того, как появился golden-акцент и пара
шрифтов Unbounded/Golos Text, уже описанные ниже в «Дизайн-система» как
EDGE 2.0: сначала обкатано изолированно на `public.html` (в новом файле
`styles-edge2.css`), затем, после одобрения, раскатано на все ~20 страниц.
Моя более ранняя версия этого раздела предполагала, что источник — EDGE 3.0
«ICE SLATE»; это было ошибкой (перепутал две разные редизайн-сессии) — палитра
«ICE SLATE» фиолетовая/мятная/маджента, а не золото-бирюза-рыжий, который
реально получился по фин-тех референсам. Значок `.brand-mark` тоже
доведён до конца в рамках этой же волны: перебраны и отклонены несколько
вариантов (буква «E» из осколков — читалась как иконка плейлиста; вариант со
срезанным углом — читался как обычная иконка «новый файл»; золотая «E из
лезвий» — сам пользователь назвал «слишком агрессивно и дёшево»), в итоге
остановились на design — кольцо + яркая золотая дуга-акцент + компактная «E»
внутри (внутреннее имя в переписке — «J2»), раскатан на все 15 страниц с
чистым регрессионным прогоном. Проверено по реальному коду 30.08.2026:
сегодняшний `.brand-mark` во всех HTML-файлах — именно этот дизайн (`<circle>`
+ дуга `<path>` + четыре `<line>`, образующие «E»), не ромб — то есть
предыдущая версия этой записи («не видно, довели ли до конца») тоже была
неточной, редизайн знака давно в проде.

**Milestone 12** — совместное ведение канала: владелец физически хранит
данные под своим `user_id`, редактор может добавлять/редактировать ставки,
но не удалять их и не трогать банк/выводы; видит банк на чтение (иначе
дашборд для него сломан), не может его менять.

**Milestone 13** — банк/прирост банка на публичном профиле скрыты по
умолчанию (`profiles.show_bank`), остальные метрики видимость не меняют.

**Milestone 14** — заявку на доступ к каналу может подать только тот, кого
владелец заранее пригласил по email (`channel_invites`) — проверяется в
самой RLS-политике, не только в UI.

**Milestone 15** — по просьбе пользователя убран шаг «запросить доступ»:
приглашённый сразу принимает приглашение и становится редактором, без
review со стороны владельца.

**Milestone 16** — синхронизация CHECK-ограничения `bet_type` с реальными
значениями формы (`Pre`/`Live`/`Хедж`) — ограничение с Milestone 1 всё ещё
ждало старые длинные значения (`Pre-value`/`Live value`/`Попанская`),
insert/update с новыми короткими значениями падал.

### Как убирали «запросить доступ», чинили миграцию Milestone 16 и добавили общий импорт (восстановлено по скриншотам переписки)

Ещё один заход того же периода, найденный отдельно — подробности вокруг
Milestone 15/16 и соседняя, не привязанная к отдельной миграции фича общего
импорта ставок.

**Milestone 15 в деталях.** До этой правки на странице «Доступ к каналу»
было два пути получить права редактора: владелец приглашает по email, либо
любой пользователь находит чужой канал через поиск и сам жмёт «запросить
доступ», а владелец отдельно одобряет заявку. По прямой просьбе второй путь
убран целиком — ни поиска чужого канала, ни кнопки «запросить», ни
отдельного экрана одобрения не осталось. Логика упростилась до одной ветки:
владелец зовёт конкретный email — это уже осознанное решение владельца;
приглашённый видит канал в блоке «Приглашения для тебя» и жмёт «Принять» —
доступ выдаётся сразу, без второго шага review. Заодно закрыта дыра,
которая раньше была в этом потоке: если владелец убирает кого-то из списка
приглашённых, а этот человек уже успел стать редактором, — доступ у него
теперь отзывается сразу же, каскадом, а не остаётся действовать до
следующего явного «увольнения».

**Общая заготовка CSS-бага, которая с тех пор стала правилом.** В этом же
заходе найден и починен визуальный баг на публичном профиле — серая
плашка-заглушка в сетке карточек, которая выглядела как «грязная» пустая
ячейка. Причина не в самой ячейке: grid-контейнер рисует тонкие линии-
разделители между карточками через собственный фоновый `background`, а
плашка была скрыта через `visibility:hidden` — элемент не рендерится, но
физически продолжает занимать место в сетке, и фон контейнера «просвечивал»
сквозь него целиком, а не узкой линией. Почищено превращением заглушки в
обычную пустую карточку с `aria-hidden="true"` (рендерится визуально как
остальные, просто без содержимого) вместо `visibility:hidden`. Пользователь
здесь же явно попросил на будущее чинить такие визуальные хвосты
самостоятельно, не дожидаясь отдельного репорта, — с тех пор это правило,
и сам паттерн (не прятать элементы сетки через `visibility:hidden`, если
контейнер рисует свой фон) с этого момента считается известным.

**Milestone 16 — не просто синхронизация ограничения, а реальный
production-баг, найденный по пути.** Пока сверял реальные ограничения базы
для новой фичи импорта (ниже), обнаружилось, что типы ставки «Pre»/«Live» в
форме не совпадают с тем, что на самом деле разрешает CHECK-ограничение в
базе (оно всё ещё ждало старые длинные значения) — то есть **на проде в
этот момент падало каждое сохранение новой ставки с типом Pre/Live**, не
только гипотетический риск. Первая версия миграции сама себя заваливала:
она сначала пыталась перевести старые значения в новые (`UPDATE`), и только
потом ослабляла ограничение (`ALTER TABLE`) — но в момент этого `UPDATE`
ещё действовало старое строгое ограничение, которое `'Pre'` не пускало, и
скрипт падал на первом же шаге, до того как вообще доходил до сути правки.
Починено перестановкой порядка: сначала `ALTER TABLE ... ADD CONSTRAINT ...
NOT VALID` (сразу разрешает и старые, и новые значения одновременно, не
проверяя задним числом существующие строки), и только потом `UPDATE`,
нормализующий старые записи в короткую форму — тот же порядок операций
(сначала ослабить ограничение как `NOT VALID`, потом нормализовать данные),
который с тех пор считается общим правилом для любого похожего
ужесточения CHECK-ограничения в проекте. Отдельно, при диагностике этой же
ошибки, короткое время подозревалось, что проблема — в отдельной ручной
вставке данных (в упавшей строке `id`/`created_at` были проставлены явно,
чего обычная форма сайта никогда не делает) — это оказалось ложным следом,
настоящая причина была именно в порядке операций внутри самой миграции.

**Общий импорт ставок из Excel/CSV — новая страница `import.html`, без
собственной SQL-миграции** (чистый фронтенд поверх уже существующих полей
`bets`). Пользователь перетаскивает файл, сайт сам сопоставляет колонки
(дата, дисциплина, букмекер, кэф и т.д. — по названиям заголовков, с ручной
правкой сопоставления при необходимости), показывает превью с числом
валидных и пропущенных строк и причиной пропуска по каждой, затем
загружает результат в выбранный канал (личный дневник или публичный — тот
же переключатель каналов, что и везде). Парсинг `.xlsx`/`.xls`/`.csv`
выполняется прямо в браузере через SheetJS, вендоренный локально
(`vendor/xlsx.full.min.js`, версия 0.18.5 с npm) — без бэкенда и без
внешнего CDN, чтобы импорт не зависел от стороннего хостинга. Про Google
Таблицы отдельно уточнили: прямая подгрузка по ссылке ненадёжна (сам Google
блокирует такой доступ из браузера, не ограничение на стороне EDGE),
поэтому решение — честно попросить пользователя выгрузить таблицу в
`.xlsx`/`.csv` (Файл → Скачать → Microsoft Excel) и загрузить как обычный
файл; на странице импорта добавлена короткая пронумерованная мини-инструкция
именно по этому шагу. Ссылка на импорт — на Дашборде и на пустой странице
«Ставки». Заодно на этом же заходе нашли и починили баг во всех
детальных таблицах-разбивках (эджи/букмекеры/дисциплины/рынки/команды):
колонка «Матч/Пик» реально показывала только матч, сам пик (на что
конкретно ставили) терялся, если поле «Матч» было заполнено — исправлено в
общем месте (`lib.js`), под матчем мелким серым текстом теперь всегда
показан пик.

### 28.08.2026 — два реальных security-инцидента + удобство ввода

**Milestone 17 — фикс утечки личного дневника.** Найдено по прямому вопросу
пользователя («точно ли по ссылке не увидят личный дневник?»). Причина:
публичные select-политики из Milestone 7 не знали о появившемся в Milestone 8
понятии «канал» — разрешали читать ВСЕ строки владельца с публичным
профилем, включая `channel='default'`. Фронтенд сам фильтровал канал в UI,
но RLS в базе — нет, а `user_id` виден в сетевых запросах любой публичной
страницы: любой человек без регистрации мог собрать прямой запрос к
Supabase REST API и получить личный дневник в обход сайта. Фикс: политики
теперь требуют совпадения `channel` с тем единственным каналом, который
владелец явно объявил публичным.

**Контекст находки (восстановлено по скриншотам переписки).** Вопрос
возник не абстрактно, а в разгар подготовки к первому реальному тесту на
живых людях — тогда же уточнили ещё два момента для запуска: репозиторий
GitHub Pages (`nasirovrao.github.io/BetsDash/...`, тот самый `BetsDash` из
«Истока» выше) уже был живым и рабочим, и что письма подтверждения/сброса
пароля идут через встроенный email-сервис Supabase с жёстким лимитом на
проект (у Supabase это единицы писем в час, не бесплатный безлимит) — для
теста с несколькими людьми одновременно предложено либо разносить
регистрации по времени, либо подключить кастомный SMTP (Resend/Postmark/
SendGrid, у большинства есть бесплатный тариф). Сама уязвимость
проверена не только на словах: до фикса живой анонимный запрос вида
`GET /rest/v1/bets?user_id=eq.<id>&channel=eq.default` к боевому Supabase
реально возвращал личный дневник владельца (реальные 666 строк), после
применения `schema_milestone17.sql` тот же самый запрос стал возвращать
пустой список, при том что данные в базе никуда не делись — RLS блокирует
чтение, а не то, что строк физически нет.

**Milestone 18 — фикс регрессии в UPDATE-политике.** Найдено при
целенаправленном аудите «какие ещё есть дыры» сразу после 17. Фикс
Milestone 4 (WITH CHECK на UPDATE) тихо потерялся для `bets`, когда
Milestone 12 полностью пересоздавал эту политику под новым именем ради
редакторов — остался только USING. Из-за этого приглашённый редактор
технически мог переписать `user_id` чужой ставки на свой, «угнав» её в
свой личный дневник. Простое дублирование условия в WITH CHECK не спасало
(редактор, уже подставивший свой `auth.uid()`, тривиально проходил бы
проверку) — фикс сделан триггером `bets_lock_ownership`, жёстко фиксирующим
`user_id`/`channel` на значение ДО обновления, независимо от того, что
прислал клиент.

**Milestone 19** — «флет по умолчанию» (`settings.default_flat_size`) —
сумма автоматически подставляется при вводе множителя флета — и новая
карточка дашборда «Доходность по флетам». *Позже (не задокументировано в
момент реализации — найдено и подтверждено в коде 30.08.2026) подстановка
стала двусторонней: правка Суммы ($) руками пересчитывает Флет (×) обратно,
а не только наоборот — важно для той же карточки «Доходность по флетам»,
чтобы правка суммы без флета не портила её незаметно. Программная простановка
значений при открытии существующей ставки на редактирование не считается
вводом и не запускает пересчёт — сохранённые флет/сумма не перезаписывают
друг друга. Покрыто тестом `test_flat_stake_bidirectional.py`, `app.html`
строки ~245–292.*

*Карточка «Доходность по флетам» тоже прошла итерацию после первого
релиза (восстановлено по скриншотам переписки): изначально показывала
только процент («2.75%»), пользователь не понял, что это за цифра — по
разъяснению выяснилось, что это отдельная метрика доходности, посчитанная
не в долларах, а в самих флетах (для каждой решённой ставки с заполненным
флетом профит в флетах — `флет × (кэф − 1)` при выигрыше и `−флет` при
проигрыше, Push обнуляется и не считается ни в стейке, ни в профите; сумма
делится на сумму поставленных флетов). По прямой просьбе убрать проценты
карточка переименована в «Профит по флетам» и стала показывать сразу
сырое количество флетов крупно (например «+22.10»), с мелкой подписью
снизу «из 801.94 флета» для контекста — без процента вообще.*

**Milestone 20** — свои дисциплины: пользователь может добавить дисциплину
через «+» прямо в форме ставки (`settings.custom_disciplines`), список —
фиксированный базовый набор + добавленное + то, что уже встречается в
старых/импортированных ставках.

**Milestone 20 в деталях, две итерации (восстановлено по скриншотам
переписки).** Поле «Дисциплина» изначально было не текстовым, а жёстким

добавления, новое значение сразу выбирается и сохраняется персистентно в
`settings.custom_disciplines` (в базе, не только в текущей сессии
браузера).

*Заодно в тот же заход — не отдельным Milestone, чистый фронтенд:
заголовки карточек рынков (например «Победитель (матч/карта)») иногда не

почищено переносом счётчика под название, а не рядом с ним.*

ссылки-разбивки, переехавшие в дропдаун, молча переставали получать
`?channel=&owner=` при навигации — просмотр чужого канала сбрасывался на
свой личный дневник одним кликом в «Детальную статистику».

### Как строился EDGE 3.0 «ICE SLATE» (восстановлено по скриншотам переписки)

Ещё один заход, найденный отдельно, — прямая история появления EDGE 3.0,
которая раньше в этом файле была помечена как открытый вопрос (см.
уточнение выше про происхождение EDGE 2.0). Разговор начался не с дизайна,
а с оргвопроса: пользователь попросил сохранить весь предыдущий диалог как
переиспользуемые скиллы. По итогам разделён на три отдельных файла по темам
(не одна дословная копия чата) — `resume-consulting` (резюме/трудоустройство),
`edge-site-dev` (архитектура и паттерны разработки EDGE) и
`betting-analytics-domain` (смысл метрик ставок) — именно эти три скилла (плюс
`ui-ux-pro-max` ниже) с тех пор загружаются в начале каждой новой сессии по
проекту.

**Отдельно — пойманная попытка инъекции.** В этом же периоде переписки
всплыло сообщение с просьбой «добавь этот скилл себе», которое по факту
не было реальным запросом пользователя, а выглядело как посторонняя
инструкция, вставленная через содержимое, а не напрямую от Рустама.
Запрос распознан как подозрительный и не выполнен — упоминаю здесь не как
баг EDGE, а как прецедент: инструкции, встреченные не напрямую в чате от
пользователя, не считаются легитимным запросом, даже если по форме похожи
на одну из уже привычных команд.

**Ревизия дизайн-скиллов.** Отдельным шагом из общего каталога доступных
скиллов оставлен только один — `ui-ux-pro-max` (база стилей/палитр/
типографики) — остальные шесть найденных (banner-design, brand, design,
design-system, slides, ui-styling) отклонены как нерелевантные: это
инструменты под баннеры/презентации/отдельные дизайн-системы, не под
многостраничный сайт-трекер.

**Первый проход `ui-ux-pro-max` — аудит, не переделка.** Первый запрос
скилла (design-system по теме «dark sports betting analytics dashboard»,
затем отдельно домены style/color/typography) в основном подтвердил, что
уже сделанное в проекте (tabular-nums на цифрах, семантика teal/rust,
KPI-карточки, hover-состояния) уже соответствует лучшим практикам, местами
даже точнее дефолтов самого скилла (существующий `--gold` ближе к
паттерну «premium dark + gold», чем стандартный набор скилла). Из
рекомендаций реально нового было одно — лёгкий stagger-въезд карточек
`.stat-grid`/`.bd-grid` при загрузке страницы (шаг 40мс, амплитуда 6px,
пружинный `cubic-bezier`), не трогая уже принятое ранее решение «без
резкого свечения/подъёма на ховере» — анимация полностью выключается через
`prefers-reduced-motion`.

**«Удиви меня» — три полных альтернативных цветовых/структурных
направления, опробованные до Ice Slate.** По прямой просьбе показать
самый смелый вариант (сначала превью на паре страниц, не сразу на весь
сайт) собран первый черновой рестайлинг — Aurora UI (усиленный
градиентный фон) + Glassmorphism (карточки-стекло) + Bento (Профит на
дашборде выбит в гигантский светящийся блок) + сдержанный HUD-акцент
(угловые засечки как на приборной панели) + полоса-статус слева на
карточках букмекеров и в ленте ставок (win/loss/sold читается ещё и по
форме, не только по цвету), палитра teal/rust/gold не менялась. Собран
только как отдельные `*-preview.html`-файлы рядом с рабочими страницами,
прод не тронут. По следующей просьбе «покажи что-то новое, цвета
поменяй полностью» — собраны ещё три отдельных варианта с другими
палитрами и структурными идеями, тоже только превью:
- **v2 «Violet Ticker»** — индиго/фиолетовый акцент вместо золота,
  позитив — электрический мятный, негатив — маджента; верхний ряд KPI на
  дашборде превращён в горизонтальную биржевую ленту вместо сетки
  карточек.
- **v3 «Copper Vegas»** — тёплая медь/янтарь на тёплом почти-чёрном фоне
  (не холодном), позитив — оливково-лаймовый, негатив — бордовый;
  карточки плотные, с видимой рамкой и лёгким «зубчатым» верхним краем
  (абстрактный намёк на ребро игровой фишки, без буквальных
  казино-иконок), плоская тень вместо мягкого свечения.
- **v4 «Ice Slate»** — холодный сине-стальной, позитив — цианово-мятный,
  негатив — холодный коралл; сознательная противоположность первому
  смелому варианту по характеру — вообще без blur/glow/теней, ставка на
  воздух, широкий трекинг в лейблах, волосяные линии. Сдержанность как
  приём, а не как недоработка.

Шрифты (Unbounded/Golos Text/JetBrains Mono/AST19) сознательно не
трогались ни в одном из вариантов — это единственные проверенные в проде
на кириллицу, менять их вслепую в рамках дизайн-эксперимента означало бы
риск незаметно сломать русский текст.

**Выбор пал на v4 «Ice Slate»**, раскатан на все 16 страниц третьим слоем
`styles-edge3.css` поверх `styles.css` → `styles-edge2.css` — ничего из
предыдущих слоёв не удалено, весь заход можно откатить одним куском. По
пути найден и починен побочный эффект самого выбора — плотная брусковая
AST19 при новом, более широком межбуквенном интервале нав-бара стала
местами сливаться в пунктах меню в одну строку; `margin-right` на
`.nav-pill` увеличен с 5px до 22px, добавлен тонкий разделитель-точка
между пунктами.

**Фокус-режим на дашборде** — по прямой просьбе анимированного
взаимодействия («навёл курсор на Банк — он скрывает остальные 7 плашек,
даёт детали по банку — и так по всем 8 вкладкам»): наведение на любую из
8 карточек статов гасит и сжимает остальные семь, наведённая укрупняется
(×1.42) и раскрывает тот же график/разбивку, что раньше уходила в
плавающий поповер сбоку — не новая фича с нуля, переиспользован уже
существующий расчёт данных (`initStatCardPopovers`/`renderSparkline` в
`lib.js`), изменилось только, где и как это показывается. На
тач-устройствах (нет реальной мыши) сетка остаётся обычной статичной —
эффект завязан на `(hover: hover) and (pointer: fine)`; клавиатурная
доступность (Tab по карточкам) не пострадала — там по-прежнему поднимается
старый плавающий поповер. Два регрессионных теста, проверявших именно
floating-поповер и `display:grid` на десктопе, пришлось переписать под
новую механику; остальной регресс-набор (`test_all.py` + 19 отдельных
тестов) прошёл без переписывания. SQL-миграций эта волна правок не
потребовала вообще — новый CSS-слой, небольшая правка `lib.js` и
`<link>` на 16 HTML-страницах, ни новых полей, ни новых запросов к
Supabase не появилось.

**Финальный цвет — не Ice Slate, а поверх него.** Уже после раскатки v4
пользователь прислал референс-скриншот с другой палитрой и неоновым
свечением на исходе ставки и попросил применить именно её: фиолетовый
акцент (`#a78bfa`), мятно-зелёный на позитиве (`#6ee7a0`) и
маджента-розовый на негативе (`#fb5aa4`) — с неоновым свечением на бейдже
результата, W/L-пилюлях, точках «Текущей серии» и полосе-индикаторе слева
на карточках/строках таблиц. Это ближе по цвету к раннему варианту
«Violet Ticker» (v2 выше), но с добавленным неоновым эффектом, которого не
было ни у v2, ни у выбранного структурно v4 — то есть сегодняшний
`styles-edge3.css` называется «ICE SLATE» по имени CSS-слоя (структурная,
сдержанная логика v4 — воздух, волосяные линии, без базового
blur/glow/теней), но реальная **палитра, которая сейчас в проде** —
фиолет/мята/маджента с точечным неоновым свечением строго на сигнале
победы/поражения ставки; нейтральные статусы («в игре», Push, Продана,
Хедж) свечения сознательно не получили — это не победа и не поражение.
Применяется через общие переменные `--gold`/`--teal`/`--rust`, поэтому
раскатилось сразу по всему сайту через один файл, не по страницам
отдельно. Проверено по реальному коду 30.08.2026 — значения в
`styles-edge3.css` (`--gold: #a78bfa`, `--teal: #6ee7a0`, `--rust:
#fb5aa4`) совпадают с описанным здесь.

**Финальный QA-прогон по итогам всей волны** — 13 приватных страниц плюс
мобильная раскладка (390px) и проверка контраста: горизонтального
переполнения нигде нет, палитра применяется единообразно по всему сайту
через общие переменные, неоновое свечение корректно ограничено именно
результатом ставки, контраст текста в норме (мятный на тёмном — 12:1,
маджента на тёмном — 6.3:1, тёмный текст на фиолетовой кнопке — 6.9:1, все
значения выше порога WCAG AA 4.5:1), мобильная раскладка складывает
карточки дашборда в один столбец без обрезки. Одно ложное срабатывание
поймано в собственном тестовом скрипте (скриншот снят до того, как
доиграла анимация появления карточек) — к самому сайту отношения не имеет.

### 30.08.2026 — решение: развивать EDGE как платформу для капперов

Не Milestone (ничего ещё не реализовано), но важная точка в пути проекта,
поэтому фиксирую здесь же. До сих пор EDGE обсуждался и строился как
инструмент — сначала личный дневник, потом с публичными каналами и
совместным ведением. Сегодня явно сформулировано видение шире: платформа,
где любой каппер/стример/блогер ведёт публичный прозрачный журнал вместо
Excel, пользователи следят за несколькими капперами сразу, и это
монетизируется (подписка на журнал, доля с подписок на капперов, реклама
букмекеров).

При разборе выяснилось, что часть этого видения технически уже реализована
задним числом, просто не как продуктовое позиционирование: регистрация
открытая, любой может завести публичный профиль (`profile-settings.html` →
юзернейм + галочка) со своей полной статой, лента `feed.html` — уже
зачаток соц-сети. То есть Milestone 1–22 (личный дневник → публичные
каналы → профиль v2 → лента) сложились в основу платформы ещё до того, как
платформа была явной целью.

Определена приоритетная задача №1 для реализации: метка «источник пика» на
своей ставке (своя ставка / юзернейм каппера, с автодополнением) + новая
вкладка «По капперам» в разбивках с полной статой по каждому источнику —
даёт пользователю, ставящему по нескольким рассылкам сразу, раздельный
трек-рекорд по каждому капперу без необходимости заводить тому капперу
аккаунт. Вотчлист (подписка на публичные профили капперов на платформе +
уведомления) — отдельная, более крупная задача вторым шагом.

Полный разбор видения, порядок монетизации и обоснование приоритетов — в
отдельном `ROADMAP-PLATFORM.md`; статус реализации самой задачи — в
`CHANGELOG.md` → «В очереди».

## Дизайн-система отдельной нитью

Не привязана к номерам Milestone один-в-один — это визуальные вехи сами по
себе:

- **`styles.css`** — «исходная база» только в смысле «слой, который все
  остальные переопределяют», а не первый вариант дизайна: сам файл — это
  уже результат ребрендинга CyberValue → EDGE 25.08.2026 (индиго `#7c6cff`,
  Space Grotesk/Inter, см. «Исток» выше). Более раннего, золотого варианта
  файла не сохранилось.
- **EDGE 2.0** (`styles-edge2.css`) — второй премиальный рестайлинг:
  индиго → золото (`--gold`), Space Grotesk/Inter → Unbounded/Golos Text
  (обе реально спроектированы под кириллицу). Обкатан сначала только на
  `public.html`, потом раскатан на все страницы.
- **EDGE 3.0 «ICE SLATE»** (`styles-edge3.css`) — имя слоя от структурного
  направления v4 из 4 опробованных (самый холодный и сдержанный, без
  blur/glow/теней), но реальная палитра, которая сейчас в проде, — более
  поздняя правка поверх неё: фиолетовый акцент вместо голубого,
  мятно-зелёный вместо бирюзы на позитиве, маджента-розовый вместо rust на
  негативе, с точечным неоновым свечением строго на исходе ставки. Полная
  история выбора (все 4 варианта, откуда взялась именно эта палитра) — в
  подробностях выше, «Как строился EDGE 3.0 «ICE SLATE»». Фокус-режим
  наведения на карточках дашборда — там же.

  **Откуда взялся шрифт пунктов меню AST19 (восстановлено по скриншотам
  переписки).** Изначально был JetBrains Mono, замена начата по прямому
  фидбеку жены пользователя («выглядит стрёмно, как супер ранняя версия»).
  Разбор начался с топовых бутиковых шрифтов из статьи Skillbox «Топ
  шрифтов года» (Evil Martians, Contrast Foundry, TypeMates, Paratype и
  т.д.) — почти все оказались платными/коммерческими (от €30–150+ за
  начертание), не бесплатными Google Fonts. Сузили до 5 кандидатов
  (Reckless, JAF Lapture, BBKV Pixel, Martian Grotesk, AST19), вживую
  протестировали только свободные — Martian Grotesk (Evil Martians, open
  source, лицензия OFL, кириллица на 11 языков) и AST19 (Анастасия
  Прогацкая, брусковая антиква с засечками, кириллица есть, автор
  распространяет свободно на Яндекс.Диске); BBKV Pixel в каталоге автора не
  нашёлся (либо переименован, либо снят с продажи), Reckless и JAF Lapture
  остались только как платные триалы, их не трогали. Выбор пал на **AST19**,
  вендорится локально (`vendor/fonts/ast19-normal.woff2`) — важно не
  грузить его с личного Яндекс.Диска автора напрямую на проде (это личная
  раздача, не CDN), и не переопределять font-weight на другое значение (у
  шрифта есть только начертание Regular, иначе браузер подставляет грязный
  синтетический bold). Раскатан на `.nav-pill` сразу на всех ~20 страницах.

  По пути ролловаута нашли и починили два бага: первый — сам же и внёс,
  AST19 заметно шире JetBrains Mono по символам, из-за чего пункт меню
  «CLV TRACKER» перестал помещаться в строку и обрезался с края — почищено
  увеличением зазора между пунктами `.nav-pill` (с 5px до 22px) плюс тонким
  разделителем-точкой посередине зазора, чисто визуальным
  (`pointer-events:none`), чтобы не съедать кликабельную зону пункта.
  Второй — не связан со шрифтом: в ленте ставок месяцы иногда дублировались
  («июль 2026» и «июнь 2026» встречались по несколько раз с разными числами
  вместо одной группы на месяц). Причина — в тестовом mock-клиенте
  (`app_test8/supabase-client.js`): составная сортировка
  `.order('bet_date').order('created_at')` вместо «сортировать по первому
  правилу, при равенстве — по второму» тупо пересортировывала весь массив
  заново на каждый отдельный `.order()`, и последнее правило (`created_at`)
  полностью перебивало первое. На реальном Supabase не воспроизводится
  (там честный SQL `ORDER BY`) — баг жил только в тестовом окружении, но
  раз всплыл, почищен и там же поправлен тест импорта, случайно завязанный
  на то же неправильное поведение.
  Позже в этом же файле — компактный нав-бар (после разрастания до 11
  пунктов, Milestone 23-фоллоуап) и, сегодня, компонент выпадающего пункта
  меню (Milestone 25).
- **Профиль v2 + Лента ставок** (`styles-edge4.css`) — визуальный язык из
  прототипа «лента а-ля X», но на существующих токенах сайта, не отдельная
  палитра. Классы с префиксами `.pf-`/`.feed-`.
- **Единая панель статов** (`styles-edge5.css`, Milestone 24) — см. выше.

Отдельно: тёмная/светлая тема переключается явно (`theme-toggle.js`,
`data-theme` на `<html>`, дефолт — тёмная), импорт ставок из Excel/CSV —
через локально вендоренный SheetJS (`vendor/xlsx.full.min.js`), без внешнего
CDN и без бэкенда.
